# Plugin Cron (`@trinacria/cron`)

Il plugin cron integra la schedulazione job in Trinacria.

Fornisce:

- discovery dei provider job tramite `ProviderKind`
- schedule a intervallo e tramite espressione cron
- rebuild sicuro a runtime quando moduli vengono aggiunti/rimossi
- protezione overlap (`allowConcurrent`)
- hook opzionali di lock per singolo job (coordinamento multi-istanza)

## Installazione

```bash
npm i @trinacria/cron @trinacria/core
```

## Avvio rapido

```ts
import { TrinacriaApp, createToken, defineModule } from "@trinacria/core";
import {
  createCronPlugin,
  cronProvider,
  type CronJobProvider,
} from "@trinacria/cron";

const JOBS = createToken<CronJobProvider>("JOBS");

class AppJobs implements CronJobProvider {
  jobs() {
    return [
      {
        name: "heartbeat",
        schedule: { type: "interval", everyMs: 10_000 },
        run: async () => {
          // lavoro
        },
      },
      {
        name: "weekday-report",
        schedule: { type: "cron", expression: "0 9 * * 1-5" },
        run: async () => {
          // lavoro
        },
      },
    ];
  }
}

const JobsModule = defineModule({
  name: "JobsModule",
  providers: [cronProvider(JOBS, AppJobs)],
  exports: [JOBS],
});

const app = new TrinacriaApp();
app.use(createCronPlugin({ cronTickMs: 1_000 }));
await app.registerModule(JobsModule);
await app.start();
```

## Opzioni `createCronPlugin`

- `cronTickMs?: number` intervallo tick per valutare espressioni cron (default: `1000`)
- `onError?: (error, job) => void` chiamata quando `job.run(...)` fallisce
- `onEvent?: (event) => void` callback telemetria strutturata a fine run
- `retry?: CronRetryPolicy` policy retry di default per tutti i job
- `lock?: CronJobLockHooks` hook opzionali di lock per singolo job
- `lockRenewIntervalMs?: number` intervallo renewal per lock handle con `renew()` (default: `10000`)

### Hook `lock`

- `onBeforeRun(job, context)`
  - ritorna un lock handle (`{ release() }`) per eseguire il run
  - ritorna `null` per saltare il run
- `onLockNotAcquired(job, context)`
  - chiamata quando `onBeforeRun` ritorna `null`
- `onAfterRun(job, context, result)`
  - riceve stato finale:
    - `success`
    - `error`
    - `skipped-lock`
    - `skipped-overlap`

## Contratto job

Un provider deve implementare:

```ts
interface CronJobProvider {
  jobs(): CronJobDefinition | readonly CronJobDefinition[];
}
```

`CronJobDefinition`:

- `name: string`
- `schedule`
  - `{ type: "interval", everyMs: number }`
  - `{ type: "cron", expression: string }` (formato 5 campi)
- `run(context)`
- `runOnInit?: boolean`
- `allowConcurrent?: boolean` (default: overlap saltati)
- `retry?: CronRetryPolicy` override per-job

Execution context:

- `scheduledAt`: momento di trigger dello scheduler
- `startedAt`: inizio reale esecuzione

Payload evento telemetria:

- `jobName`, `status`, `attempts`
- `scheduledAt`, `startedAt`, `finishedAt`, `durationMs`
- `error`, `releaseError` se presenti

## Formato espressione cron

Il plugin usa i classici 5 campi:

```text
minute hour dayOfMonth month dayOfWeek
```

Sintassi supportata:

- wildcard: `*`
- lista: `1,2,3`
- range: `1-5`
- step: `*/5`, `1-10/2`

Esempio:

- `*/15 9-17 * * 1-5` ogni 15 minuti in orario ufficio nei giorni feriali

## Comportamento runtime

Flusso startup:

1. il plugin scopre provider marcati con `CRON_JOB_PROVIDER_KIND`
2. i job vengono validati
3. lo scheduler avvia i timer
4. i job con `runOnInit` eseguono una volta subito

Cambi modulo runtime:

- su register/unregister modulo, lo scheduler esegue rebuild dai provider correnti

Shutdown:

- tutti i timer vengono fermati
- i run in-flight vengono attesi (`Promise.allSettled`)

## Esempio lock distribuito per-job (Prisma/DB)

```ts
app.use(
  createCronPlugin({
    lock: {
      async onBeforeRun(job) {
        const lock = await lockService.acquire(job.name, 30_000);
        if (!lock) return null;

        return {
          release: () => lockService.release(job.name, lock.lockToken),
        };
      },
      onLockNotAcquired(job) {
        logger.debug(`Lock non acquisito per ${job.name}`);
      },
    },
  }),
);
```

## Note per ambienti multi-istanza

- usa backend lock condiviso (Redis/Postgres/altri DB condivisi)
- usa sempre TTL lock e release in `finally`
- se i run possono superare il TTL, implementa renewal del lock
- definisci policy esplicita su errori lock backend (fail-open vs fail-closed)
