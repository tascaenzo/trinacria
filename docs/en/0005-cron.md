# Cron Plugin (`@trinacria/cron`)

The cron plugin integrates job scheduling into Trinacria.

It provides:

- job provider discovery through `ProviderKind`
- interval and cron-expression schedules
- runtime-safe rebuild when modules are added/removed
- overlap protection (`allowConcurrent`)
- optional per-job lock hooks for multi-instance coordination

## Installation

```bash
npm i @trinacria/cron @trinacria/core
```

## Quick start

```ts
import { TrinacriaApp, createToken, defineModule } from "@trinacria/core";
import {
  createCronPlugin,
  cronProvider,
  type CronJobProvider,
} from "@trinacria/cron";

const JOBS = createToken<CronJobProvider>("JOBS");

class AppJobs implements CronJobProvider {
  jobs() {
    return [
      {
        name: "heartbeat",
        schedule: { type: "interval", everyMs: 10_000 },
        run: async () => {
          // do work
        },
      },
      {
        name: "weekday-report",
        schedule: { type: "cron", expression: "0 9 * * 1-5" },
        run: async () => {
          // do work
        },
      },
    ];
  }
}

const JobsModule = defineModule({
  name: "JobsModule",
  providers: [cronProvider(JOBS, AppJobs)],
  exports: [JOBS],
});

const app = new TrinacriaApp();
app.use(createCronPlugin({ cronTickMs: 1_000 }));
await app.registerModule(JobsModule);
await app.start();
```

## `createCronPlugin` options

- `cronTickMs?: number` tick interval for evaluating cron expressions (default: `1000`)
- `onError?: (error, job) => void` called when `job.run(...)` throws
- `onEvent?: (event) => void` structured telemetry callback on run completion
- `retry?: CronRetryPolicy` default retry policy for all jobs
- `lock?: CronJobLockHooks` optional per-job run lock hooks
- `lockRenewIntervalMs?: number` renewal interval for lock handles exposing `renew()` (default: `10000`)

### `lock` hooks

- `onBeforeRun(job, context)`
  - return a lock handle (`{ release() }`) to execute the run
  - return `null` to skip the run
- `onLockNotAcquired(job, context)`
  - called when `onBeforeRun` returns `null`
- `onAfterRun(job, context, result)`
  - receives final result status:
    - `success`
    - `error`
    - `skipped-lock`
    - `skipped-overlap`

## Job contract

A provider must implement:

```ts
interface CronJobProvider {
  jobs(): CronJobDefinition | readonly CronJobDefinition[];
}
```

`CronJobDefinition`:

- `name: string`
- `schedule`
  - `{ type: "interval", everyMs: number }`
  - `{ type: "cron", expression: string }` (5-field format)
- `run(context)`
- `runOnInit?: boolean`
- `allowConcurrent?: boolean` (default behavior is skip overlap)
- `retry?: CronRetryPolicy` per-job override

Execution context:

- `scheduledAt`: scheduler trigger time
- `startedAt`: actual execution start time

Telemetry event payload includes:

- `jobName`, `status`, `attempts`
- `scheduledAt`, `startedAt`, `finishedAt`, `durationMs`
- `error`, `releaseError` when present

## Cron expression format

The plugin uses standard 5 fields:

```text
minute hour dayOfMonth month dayOfWeek
```

Supported syntax:

- wildcard: `*`
- list: `1,2,3`
- range: `1-5`
- step: `*/5`, `1-10/2`

Example:

- `*/15 9-17 * * 1-5` every 15 minutes during business hours on weekdays

## Runtime behavior

Startup flow:

1. plugin discovers providers tagged with `CRON_JOB_PROVIDER_KIND`
2. jobs are validated
3. scheduler starts timers
4. jobs with `runOnInit` execute once immediately

Runtime module changes:

- on module register/unregister, scheduler rebuilds from current providers

Shutdown:

- all timers are stopped
- in-flight runs are awaited (`Promise.allSettled`)

## Per-job distributed lock example (Prisma/DB)

```ts
app.use(
  createCronPlugin({
    lock: {
      async onBeforeRun(job) {
        const lock = await lockService.acquire(job.name, 30_000);
        if (!lock) return null;

        return {
          release: () => lockService.release(job.name, lock.lockToken),
        };
      },
      onLockNotAcquired(job) {
        logger.debug(`Skipped lock for ${job.name}`);
      },
    },
  }),
);
```

## Notes for multi-instance environments

- use a shared lock backend (Redis/Postgres/another shared DB)
- always use lock TTL and release in `finally`
- if runs can exceed TTL, implement lock renewal strategy
- decide explicit policy for lock backend errors (fail-open vs fail-closed)
